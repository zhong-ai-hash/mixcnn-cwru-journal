## 4. 本次新增：GPU 代码修正

### 4.1 12 GB 显存

4096 点输入、batch 128 时，CPU 端单进程工作集已达 6.6 GB；4 个 worker
在 3080Ti 上会 OOM。`engine.py` 新增：

```text
auto_batch(128, 1024) = 128
auto_batch(128, 4096) = 32，梯度累积 4 步，等效 batch 仍为 128
```

评估与 BN 重校准也走同一 `auto_batch`，避免 eval 阶段再次爆内存。

### 4.2 单 job 失败不再中断矩阵

`suite.py` 现在捕获每个 future 的异常，写 `failures.jsonl` 并继续；
进程池改用 `spawn`，避免 Linux 下 CUDA fork 的不确定性。

### 4.3 外推系数

`benchmark.py` 修正两处：

- M1c 从 `×480` 改为 `×80`（6 变体 × 2 条件 × 2 臂 × 20 种子 / 6 = 80/模型）；
- JNU 原来只算了一个平均模型，现改为 `sum(CWRU 成本) × JNU 因子 × 60`。

### 4.4 汇总字段

每个 run 现在记录：

```text
train_secs / eval_secs / secs
n_classes / params
per-class recall（clean 与每档 SNR）
macro-F1（clean 与每档 SNR）
clean 混淆矩阵
split_meta（overlap_bearings / overlap_files / overlap_samples）
```

`summary.json` 新增 `contrasts`：

```text
lobo vs recording-random
lobo vs window-random
recording-random vs window-random
bearing-grouped vs file-random
sample-grouped vs window-random
```

这样“切分单位”的效应不用手算，直接进表。

## 9. 运行开销字段（11-24）

新增字段已进入 `engine.py` / `suite.py`，并同步到仓库：

```text
每个 run JSON : epoch_secs, epoch_secs_mean, train_windows_per_s,
                eval_windows_per_s, peak_alloc_mb, peak_reserved_mb,
                micro_batch, grad_accum
每个 suite    : summary.json -> overhead
                runtime.json -> sessions[] + total_secs
                manifest.json -> total_secs_all_sessions
                runs.csv -> 全部开销字段
```

`runtime.json` 的意义：矩阵中断重跑时，`elapsed_secs` 只表示最后一次
进程，不能写进论文；ledger 把每次 session 相加，得到真实总墙钟。

论文口径：成本表与精度、参数量、FLOPs、峰值显存并列，不单独宣称
“训练很快”。

`benchmark.py`（20 epoch、20 draws、5 BN 库，单进程）实测：

| 模型 | 训练 s | 评估 s | 合计 s | clean acc |
|---|---:|---:|---:|---:|
| base | 5.0 | 24.8 | 30.8 | 90.2 |
| noPad | 3.1 | 7.1 | 10.2 | 97.6 |
| nores | 2.8 | 22.2 | 25.1 | 88.8 |
| soft | 4.7 | 32.5 | 37.3 | 89.0 |
| multi | 3.3 | 7.4 | 10.7 | 93.6 |
| soft_multi | 3.5 | 7.7 | 11.2 | 92.8 |
| wdcnn / resnet1d / drsn1d / tcn / transformer | 2.6–5.3 | 5.1–19.3 | 7.7–24.2 | 61.8–85.0 |

Paderborn（3 类、10,080 训练窗）单 run 约 6.8 分钟，是矩阵的主要成本项。

**协议调整（实测后）**：评估抽样 20 → 10 次，BN 库
`clean / 0 dB / 4 dB` 三套（原五套含 −4、8 dB）。单 run 降到 20.6 s
（训练 4.5 + 评估 16.1）。12 worker 实测吞吐 5.6 run/min，主矩阵
2880 run 约 8.5 h。

**本轮修的三个真问题**：

1. `engine.run_job` 未把张量搬到 GPU，`xtr[idx]` 直接报设备不一致；
2. 强杀父进程后 8 个 `multiprocessing.spawn` 孤儿仍占 GPU，所有测速失真
   （清理后单 run 从 5 分钟回到 45 秒）；
3. `SHA256SUMS` 在 Windows 检出为 CRLF，Linux `sha256sum -c` 全部失败，
   已在仓库固定 LF 并注明只校验 `.npz`。

**断点续跑保护**：每个 run JSON 现在带 `cfg_stamp`（epochs/batch/lr/
draws/snrs/bn_banks），只有完全一致才跳过，避免不同协议的结果被静默复用。

### 11.2 BN 实现错误：旧数字不能进入最终表

旧 `engine.recalibrate_bn` 同时存在三个问题：

1. 按文件顺序切校准 batch，单个 batch 集中在少数录音上；
2. `reset_bn` 使用 `momentum=None`，等价于各 batch 无偏方差等权累计，
   丢掉 batch 间方差；
3. 校准 batch 过大（256），训练集只有约 6 个 batch。

结果是 `running_var` 被系统性低估。最强证据是自校准对照
（clean 训练 + clean BN 库 + clean 测试，同一分布、同一模型，仅重估
BN 统计量）：

| 变体 | self-Δ（百分点） |
|---|---:|
| base | -17.1 |
| multi | -24.6 |
| noPad | -21.1 |
| nores | -15.6 |
| soft | -17.5 |
| soft_multi | -24.7 |

单例 `lobo0/base/seed0` 为 93.6% → 79.6%。这不能解释为噪声失配，
只能解释为实现偏差。

## 12. 下一步执行顺序（2026-11-25）

1. AutoDL 开机后先跑 2 个 20-epoch 冒烟 run，输出到独立目录：

   ```bash
   python suite.py --suite main --models base --splits lobo0 --seeds 0 \
     --limit 2 --epochs 20 --draws 10 --bn-snrs 0 4 --jobs 1 \
     --device cuda --save-state --save-probs \
     --out-dir results/gpu_v2/smoke
   ```

2. 只有 **clean 训练**的 `bn_self_delta` 落在 **±0.5** 内，才允许放主矩阵；
   noise 训练的条件只记录、不作通过标准。
3. 重跑 `main`（约 6–6.5 h）：

   ```bash
   python code/gpu/suite.py --suite main --jobs 12 --device cuda \
     --draws 10 --bn-snrs 0 4 --save-state --save-probs \
     --out-dir results/gpu_v2/main
   ```

4. 重跑 `jnu`（约 0.7–1 h，使用 1,464 窗与 `--micro-batch 128`）：

   ```bash
   python code/gpu/suite.py --suite jnu --jobs 12 --device cuda \
     --draws 10 --bn-snrs 0 4 --micro-batch 128 \
     --out-dir results/gpu_v2/jnu
   ```

5. `baselines`、`m1c`、`paderborn`、`seu` 不重跑；BN 不是它们的主线。
6. 回传后重建全部表，重跑 `stats.py`：
   - TOST margin 改为预注册的 ±1.0；
   - TOST 用于**变体间**等价性，不再用于 noise−clean 的 50 点差；
   - 方差分解按 `kind` 分开，不把 LOBO / recording / window 混池；
